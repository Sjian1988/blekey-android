# 协议速查

> **说明**：以下内容是对本人自有车盒通信行为的观察结论，**不是官方协议规范**。不同车型、不同车盒固件版本可能不一致，适配前请先抓包核对。
> 本文只描述协议层结论，不含任何第三方应用的代码或其逆向过程资料。

## 1. GATT 层

| 项 | 值 |
| --- | --- |
| 服务 UUID | `8849a9d0-d75f-0c8c-2348-de2d580f2f24` |
| 收发特征 | `8849a9d1-d75f-0c8c-2348-de2d580f2f24`（写 + notify，同一特征） |
| 日志特征 | `8849a9d2-d75f-0c8c-2348-de2d580f2f24` |
| MTU | 247 |
| 写类型 | `WRITE_TYPE_NO_RESPONSE` |
| 广播厂商 ID | `0xF715`（63253） |
| 广播厂商数据 | 前 6 字节为车机序列号 |

写通道已串行化（CCCD → MTU → 鉴权），避免早期版本「鉴权帧发不出去」的问题。

## 2. 帧格式

帧头 16 字节，小端：

| 偏移 | 长度 | 含义 |
| --- | --- | --- |
| `[0..1]` | 2 | `55 AA`（上行）/ `AA 55`（下行） |
| `[2]` | 1 | version |
| `[3]` | 1 | `type \| channel<<4` |
| `[4..5]` | 2 | sequenceId |
| `[6..7]` | 2 | cmd |
| `[8..9]` | 2 | key |
| `[10..11]` | 2 | payload 长度 |
| `[12..13]` | 2 | payload 字节求和 |
| `[14..15]` | 2 | 头部 `[0..13]` 字节求和（含上一条） |
| `16..` | n | payload |

> 校验是**逐字节求和**，不是 CRC。原实现里函数名叫 `crc8WithData`，但内部是 `sum += b[i] & 0xFF`。

**TLV**：`tag(1B) + len(1B) + value`；int 固定 4B LE，short 2B LE，byte 1B。

## 3. 密钥派生与鉴权

```
password    = 手机端生成的 6 位数字（不依赖服务器）
deviceKey   = AES-ECB-NoPadding( pad(password, 16), pad(车机序列号Hex大写, 16) )
keyPass     = hex(deviceKey)                      // 32 字符，存本地
校验值      = AES-ECB-NoPadding( keyPass, 车机下发的 random(16B) )
```

流程：`请求鉴权(6/0)` → 车机回 `AuthResp`（含 random）→ `下发设备密钥(6/1)` → `校验设备密钥(6/2)` → `ready`。

配对成功后设备密钥只存在本机 `SharedPreferences`，之后完全离线。车机同一时间只认一个绑定的手机，换客户端前需在原厂 App 里解绑。

## 5. `cmd=2` 响应 TLV

| tag | 含义 | 长度 | 说明 |
| --- | --- | --- | --- |
| 23 | 电量 | 1B | 百分比 0~100 |
| 24 / 25 / 26 | 版本 主 / 次 / 修订 | 2B | 例如 1.2.2 |
| 27 | 设备类型 | 4B | 1 车钥匙 / 2 车盒 |
| 28 | 平台 | 4B | 1 ATK / 2 NORDIC / 3 REALTEK / 4 ONMICRO / 5 REALTEK8773 |
| 29 | 配对号 | 4B | |
| 30 | 绑定状态 | 1B | 0 未绑定 / 1 已绑定 |
| 31 | CPU ID | nB | 设备唯一标识 |
| 32 | 电池电压 | 2B | mV，小端 |
| 33 | 充电状态 | 1B | 语义未确认，仅记录日志 |
| 34 | 车盒电源状态 | 1B | 语义未确认，仅记录日志 |
| 35 | 车型 | 4B | |

要点：

- 电量是单字节百分比；电压是 2 字节小端 mV
- 部分固件会先回显手机发去的 tag 再回自己的 tag，**按 tag 取值，不能靠顺序**
- 车机偶尔连回两条完全相同的帧（实测间隔约 120ms），后到覆盖前到即可
- 取值时机：鉴权通过后发一次 `cmd=2 key=0`；界面 `onResume` 且数据超过 60 秒时补一次。不做定时轮询

## 6. 几个关键约定

这些规则**不是 App 定义的，是车机里保存的配置**，换客户端照样生效，客户端必须按同样的节奏发指令。

| 动作 | 车机配置 | BleKey 实现 |
| --- | --- | --- |
| 开锁 | 按 2 次，间隔 1 秒 | 点一次「解锁」连发 2 帧 `cmd=4 key=100`，间隔 1000ms（`Prefs.UNLOCK_GAP_MS`） |
| 落锁 | 关锁后及时断电 | 单发 1 帧 `cmd=4 key=101`；之后 15 秒不主动重连（`LOCK_QUIET_MS`），给车机断电留时间 |

**舒适进入**：距离判断由车机做，App 只下发阈值。`cmd=7 key=32` 的响应 payload 为 `[0]=是否开启`、`[1..2]=落锁距离 u16LE`、`[3..4]=开锁距离 u16LE`、`[5..8]=错误码 u32LE`；距离是 RSSI **绝对值**（70 表示 -70 dBm），开锁要求信号更强（数值更小）。写入用 `cmd=7 key=0`，车盒**不回执**，所以写完 700ms 重发一次 `7/32` 用真实值校准。

**无法读回锁配置**：`7/1`、`7/4`、`7/3` 全是 setter，唯一能读回的是 `7/32`。因此开锁节奏固定写在客户端里，BleKey 不会去改车机的开锁 / 落锁配置。

## 7. 调试

```bash
adb logcat -s BleKey
```

App 内「高级设置 → 运行日志」也能看每一帧收发的原始 hex（`rx cmd=.. key=..`），对照上面的指令表即可定位卡在哪一步。
