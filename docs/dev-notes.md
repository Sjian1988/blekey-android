# 蓝牙车钥匙 BleKey

一个只做"靠近车机自动连上 + 解锁"的最小 App, 用来替代原「红树河熊」App 的连接部分。
原 App 保留着刷固件、改设置用。

---

## 为什么换掉原 App 的连接逻辑

原 App 的连接链路(`AutoConnect` / `BleProfileManager`):

```
每 10 秒 tick 一次 → connect(device).useAutoConnect(false).retry(3,100)
                   → 15 秒连接超时 → 断 → 再等 10 秒 → 失败后退化成扫描 20 秒
```

`autoConnect=false` 意味着**必须靠 App 主动发起并等待连接**, 设备不在范围内就只能空等超时。
加上 Android 8.1+ 对后台无过滤扫描的限制(原 App 用的是空 `ScanFilter`), 后台基本扫不到车,
所以经常"必须手动打开 App 才连上"。

BleKey 的做法:

| | 原 App | BleKey |
|---|---|---|
| 连接方式 | `useAutoConnect(false)` + 轮询直连 | `connectGatt(ctx, true, ...)` 交给控制器自动连接白名单 |
| 需要扫描吗 | 需要, 且后台扫描受限 | 不需要。设备广播一出现, 控制器直接建连 |
| 靠近到可用 | 20~40 秒 | 目标 1~3 秒(待实测) |
| 进程被杀 | 靠 ROM 决定 | 前台服务常驻 + 开机自启 |
| 解锁 | 手动 | 通知栏按钮 / 可选 RSSI 靠近自动解锁 |

## 配对(只需要一次)

**前提**: 车机同一时间只认一个绑定的手机。原 App 已经绑着, 新 App 直接连会收到"已绑定"的回复, 所以要先解绑。

1. 打开原 App, 在设备设置里点"解绑"
2. 打开 BleKey → "搜索车机" → 找到车机 → 点"配对"
3. 车机若是"未绑定 + 允许直接配对"状态, 会自动完成;
   若提示要在车机上确认, 按车机提示按键, 重试即可

配对成功后, `设备密钥`(16 字节 AES 结果)存在本机 SharedPreferences 里, 以后不再需要联网也不需要原 App。

> BleKey 里**没有**"向车机发送解绑"按钮: 解绑只走原 App, 避免误操作把车机解绑掉。

### 需要原 App 的时候: 点"让位"

BLE 连接是独占的: BleKey 占着车机时, 原 App 连不上。
刷固件 / 改设置 / 分享钥匙 / 重新配对前, 点界面上的「**让给原 App(10 分钟)**」
(通知栏也有"让位"按钮):

- 立刻断开连接并停止自动重连
- 10 分钟内原 App 可以正常操作
- 10 分钟后自动接管回来; 期间手动点解锁/落锁会立即取消让位

## 日常使用

1. 保持通知栏那条"车钥匙"通知常驻, 不要划掉
2. 手机设置里给 BleKey(只需要做一次, App 里不再提供开关):
   - 电池 → 无限制 / 允许后台活动
   - 允许自启动
   - 最近任务里锁定(防止被清理)
3. 靠近车 1~3 秒自动连上, 通知栏点"解锁"
4. 顶部那条胶囊就是连接状态: 圆点 + `已连接` + `-46 dBm` + 信号条; 连不上时整条换色
5. 想看连接与指令记录: 高级设置 → 运行日志 → 点那一行展开(日志框固定高度、内部滚动)

开机自启、前台服务常驻、开锁连发全部**默认开启且不做成配置项**, 装好就能用。

## 界面设计与主题

界面全部是代码画的 —— 布局仍然全在 Java 里, `res/` 只有启动器图标。
设计令牌集中在 `Ui.java`, 自绘组件三个: `IconView`(24×24 坐标的 Path 图标)、
`RingView`(环形电量)、`ToggleView`(开关)。

### 双主题, 跟随系统深色模式

`Ui.applyTheme()` 按 `Configuration.uiMode` 取一套令牌, 日间/夜间各一套:

| | 日间 | 夜间 |
|---|---|---|
| 页面底 | `#F2F4F7` | `#0B0F14` |
| 卡片 | `#FFFFFF` | `#141A22` |
| 卡片内嵌块 | `#F1F5F9` | `#1B222C` |
| 卡片描边 | `#E3E7ED` | `#232B36` |
| 主文字 | `#0F172A` | `#E8EEF6` |
| 次要文字 | `#64748B` | `#8A97A8` |
| 强调色 | `#0F766E` | `#2DD4BF` |
| 压在强调色上的文字 | `#FFFFFF` | `#07231F` |

切换靠 Activity 重建完成: manifest 里**没有**声明 `uiMode` 这个 configChange,
系统改深色模式时会重建 Activity → `onCreate` → `applyTheme()` 重新取色。

> 令牌是**静态字段, View 只在构造时读一次颜色**。所以别想着运行中改令牌让界面自己变,
> 也别在 `onConfigurationChanged` 里手动处理 —— 让系统重建最省事。

### 三条纪律(改界面时别破)

来自 ui-ux-pro-max 的 UX 准则:

1. **只有一个强调色**(UX-039)。青绿是品牌色 + "正常态"; 红黄蓝只在表达状态时出现
   (绿=成功 / 红=错误 / 黄=需注意 / 蓝=进行中, UX-037)。颜色不当装饰用。
2. **状态不靠颜色单独传达**(UX-038)。连接状态是"圆点 + 文字 + 信号条"三重表达,
   去掉颜色也读得懂。
3. **触控目标够大**(UX-013/024)。三个操作块 84dp 高, 远超 44pt 下限。

### 几个视觉决定, 以及为什么

- **状态是胶囊, 不是卡片**。原来状态和电量是两张平级白卡, 最该被看见的"现在能不能用"
  反而不显眼。现在压成一条贴在最上面、会按状态变色的胶囊。
- **电量是环, 不是进度条**。大号数字 + 横条会跟页面标题抢视觉重量, 而且 100% 时
  那根满格长条承载不了任何信息。环形把百分比放圆心, 外圈直接读剩余量。
- **后备箱单独强调**。三个操作里只有它带青绿描边 + 青绿图标 —— 它是"双手拿东西"
  这个场景真正要按的那一个, 不该和落锁长得一模一样; 但也不做成填充, 免得抢主按钮。
- **卡片必须有描边**。日间白卡贴浅灰底、夜间深卡贴近黑底, 对比度都只有一点点,
  不加描边卡片边界会糊在背景里, 分层全靠猜。
- **长说明文字不用强调色**。正常状态用正文色, 只有异常才变色 —— 一整段染成青绿会一直
  跟旁边的状态值抢注意力。

### 二级页(高级设置 / 靠近自动开锁)

两个二级页共用一套排版, 组件都在 `Ui.java` 里, 加新设置项直接拼:

| 组件 | 用途 |
|---|---|
| `pageHeader(title, back)` | 返回箭头(40dp 热区, 视觉压在 16dp 边距上) + 20sp 标题 |
| `section(text)` | 分组小标题, 12sp + 字距 0.06 |
| `iconTile(type, size, fg, bg)` | 图标底座: 圆角方块 + 同色淡描边 + 居中图标 |
| `settingRow(icon, title, sub, right)` | 设置行: 左图标 + 标题/副标题 + 右侧徽章或箭头, 整行可点 |
| `badge(text, color)` | 状态徽章, 底色是该色 11% 透明(夜间 20%) |
| `outlineButton(label)` | 中性按钮: 内嵌块底 + 描边 |
| `metric(text, sp, color)` | 大号读数, 用于阈值对比 |

两页各自解决的问题:

- **高级设置** —— 原来六张白卡一模一样, 设备信息、入口、大段说明糊在一起。
  现在设备卡带钥匙底座 + 右上角绑定徽章; 入口卡带信号图标; 「后台运行」从
  "一段结论 + 两个并排按钮 + 又一段小字" 改成两行设置项(右侧直接给状态或箭头,
  点整行就动手), 脚注挪到卡片外, 卡片里只留可操作的东西。
- **靠近自动开锁** —— 原来车机值是 `已开启 · 落锁 -80 · 开锁 -70 dBm` 一行中文,
  两个数字埋在里面看不出谁大谁小。现在拆成左右两块 27sp 大读数, 中间一条竖线;
  两个阈值各占一个内嵌块, 标题 + 实时数值 + 滑块 + 两端 `-45 很近 / -95 很远` 刻度 ——
  滑块本身看不出方向, 标了刻度才知道往左拖意味着什么。

### 启动器图标

`res/` 下是 adaptive icon(前景 vector + 渐变底色) 加五档 PNG 兜底(API 23~25):

```
res/drawable/ic_launcher_background.xml   渐变底色 #0B5F58 -> #14B8A6
res/drawable/ic_launcher_foreground.xml   白色钥匙(环 + 杆 + 两齿)
res/mipmap-anydpi-v26/ic_launcher.xml     adaptive-icon + monochrome(Android 13 主题图标)
res/mipmap-*dpi/ic_launcher.png           用 tools/GenIcon.java 生成
```

**改图标就改 `tools/GenIcon.java` + `ic_launcher_foreground.xml` 两处**, 坐标基准都是
108×108, 必须同步。尺寸要按**可见区**算: 启动器只显示画布中心 66×66 那块, 图形占
可见区 75% 左右是安全区间; 按 108 满铺会顶到遮罩边缘被裁(踩过一次, 见下)。

`GenIcon` 除了 PNG 还会输出 `build/icon_mock_{square,circle}.png`, 那是按 adaptive
裁切规则模拟的桌面效果, 不装机也能判断图形有没有被切、比例合不合适。

### 通知栏 / 状态栏图标

1.3 之前 `setSmallIcon` 用的是 `android.R.drawable.stat_sys_data_bluetooth` —— 系统那个
老蓝牙符号, 所以不管桌面图标怎么换, 通知栏永远是旧的。现在换成自绘 vector:
`res/drawable/ic_stat_blekey.xml`(单色钥匙剪影)。

**小图标必须按 24dp 重排, 不能等比缩启动器那套。** 启动器线宽 5.5/108, 缩到 24 只剩
1.2dp, 状态栏里糊成一坨。这里线宽加到 2.2~2.3, 齿间距留 3.2, 是"还认得出是钥匙"的下限。
颜色只写白色: 系统取 alpha 通道自己着色(浅色面板涂深、深色涂白), 渐变和多色都会被压平。

**不要调 `setLargeIcon()`。** MIUI/HyperOS 的通知卡片布局是: 左边画应用图标, 右边画
largeIcon。两个都设就变成一对重复的图标(踩过, 已经去掉)。只留 smallIcon 时, 左边那个
就是应用图标本身, 已经是新的青绿钥匙, 右边干净。

### 踩过的坑

- **`getWindow().getInsetsController()` 在 `setContentView` 之前调会 NPE**, 真机直接崩
  (`PhoneWindow.getInsetsController()` 内部去取 DecorView, 那时还没创建)。所以
  `styleSystemBars()` 必须放在 `setContentView` 之后, 并且包了 try-catch 做二道保险。
- 旧的 `setSystemUiVisibility(SYSTEM_UI_FLAG_LIGHT_STATUS_BAR)` 在 targetSdk 34 上
  不再生效 —— 深色主题下状态栏时间/图标仍是黑的, 贴 `#0B0F14` 上等于消失。
  必须改用 `WindowInsetsController.setSystemBarsAppearance()`(API 30+)。
- 深色下强调色是亮薄荷 `#2DD4BF`, 压在上面的文字如果还用白色会糊成一片,
  必须换 `TEAL_ON = #07231F`。同理所有写死的 `0xFFxxxxxx` 在深色下都会失效,
  颜色必须从 `Ui.*` 取。
- **adaptive icon 只显示画布中心 66×66**。第一版把钥匙按 108 满铺画, 桌面模拟图里左右
  直接顶到遮罩边被切掉。图形按可见区 75% 排, 视觉上才和其它 App 图标一个量级。
- **`android.R.drawable` 里的图标不能拿来当启动器图标**(换不了, 只有罗盘/齿轮那些拟物图),
  也不能用来做快捷方式图标(系统会报 `Icon resource must reside in shortcut owner package`)。
  要么进 `res/`, 要么代码现画 —— 走的是后者。
- **加了 `res/` 之后构建多一步**: `aapt2 compile --dir res -o build/res.zip`, 而且
  `res.zip` 要作为输入传给 `aapt2 link`, 否则 `@mipmap/ic_launcher` 解析不到, link 直接失败。
- **`ToggleView` 的圆点在开启态不能用白色**。深色主题下轨道是亮薄荷, 白点压上去几乎看不出
  边界; 圆点色必须跟主按钮文字共用 `TEAL_ON`。
- **Java 里第一次引用自己的资源要改构建顺序**。`aapt2 link` 不带 `--java <dir>` 就不生成
  `R.java`; 所以 1.3 起流程变成 `compile res → link(--java build/gen) → javac(src + R.java)
  → d8`, `R.java` 是编译输入, 不能像以前那样第一步就编译 Java。
- **SystemUI 会缓存通知小图标, 换图标后可能仍显示旧的**。实测改内容、改资源 id 都刷不掉,
  得重启界面进程(`adb shell am crash com.android.systemui`, 或直接重启手机)。别被"改了没
  反应"骗了 —— 先重启 SystemUI 再判断图标画得对不对。

## 后备箱入口

电尾没有一脚踢。App 内主界面有「后备箱」按钮; 另外通知栏常驻通知上也有一个:

| 入口 | 怎么用 |
|---|---|
| App 内 | 主界面控制区点「后备箱」(`cmd=4 key=115`) |
| 通知栏 | 下拉通知栏 → 常驻通知上的 **解锁 / 后备箱 / 落锁** 三个按钮 |

通知栏第三个原来是「让位」, 换成后备箱了; 让位入口还在 App 里, 功能没丢。

### 小爱同学这条路为什么走不通(已实测否掉)

原想让小爱"打开 App"来代替手动点按钮, 实测做不到, 结论是**死的**, 别再试:

| 试过的 | 结果 |
|---|---|
| 小爱「训练计划」加"打开应用"动作 | 这版(超级小爱)训练页只有「回复文字 / 控制家庭设备 / 录屏教学」,**没有打开应用** |
| 直接说「打开蓝牙车钥匙」 | 失败 |
| 把 `label` 改成「车钥匙」再说「打开车钥匙」 | **仍然失败**(已改回原名) |

失败不是 ASR 听错, 是云端语义层直接拒绝。同一句话抓两次日志对比:

```text
说「打开微信」(成功):
  Application.Operate        ← 关键指令, 小爱只有收到它才会去启动应用
  UIController.Navigate
  SmartPower: launch com.tencent.mm/.ui.LauncherUI launchFrom=com.miui.voiceassist

说「打开车钥匙」(失败):
  Dialog.Reject              ← 只有一个拒绝
  (没有任何 Application.Operate)
```

`Application.Operate` 由**云端 NLP** 在识别出应用名后下发, 词典里是内置热门应用 + 应用商店上架应用。
本 App 是自签名的非商店应用, 进不去那份词典, **改什么名字都只会收到 `Dialog.Reject`**。

所以语音这条路停在"能把 App 打开"为止都做不到, 现在可用的入口只有:

| 入口 | 操作 |
|---|---|
| App 内 | 主界面控制区点「后备箱」 |
| 通知栏 | 下拉通知栏 → 常驻通知上的「解锁 / 后备箱 / 落锁」 |

**没有做"App 被拉起就自动开尾门"**, 试过之后否掉了:

- 等于把**「打开 App」这个无关动作**绑到**不可撤销的机械动作**上 —— 误唤醒、口令误说、
  别的 App 拉起, 都会让尾门直接弹开;
- 尾门弹开收不回来, 后面有人或有墙就是事故, 不值得换掉"点一下";
- 顺带把 `blekey://trunk` 公开深链一起删了(谁都能发, 网页点个链接也能触发)。

## 后台保活

「靠近就能连上」的前提是服务一直活着。BleKey 内置三套机制, 装好即生效:

| 机制 | 实现 | 作用 |
|---|---|---|
| 前台服务 | `BleKeyService` + `foregroundServiceType=connectedDevice` | 系统优先级最高的一档; `onTaskRemoved` 里不退出, 划掉最近任务也不断连 |
| 周期任务 | `KeepAliveJob`(JobScheduler, 15 分钟, `setPersisted`) | 进程被清掉后把服务拉回来, 重启后依然有效 |
| 闹钟兜底 | `KeepAliveReceiver`(`setAndAllowWhileIdle`) | Doze 休眠下也能醒, 和 Job 互相续期 |

还有两件事 App 自己做不了, 只能你在系统里点一下(界面「后台运行」区块有两个按钮直达):

1. **电池白名单**(省电策略 → 无限制)。不加的话锁屏久了会被冻结; 更要紧的是 Android 12+
   会**禁止后台启动前台服务**, 而没有白名单的 App 正好在禁止名单里 —— 这直接导致"靠近连不上"。
2. **自启动**。不加的话重启手机后服务不会自己起来(BootReceiver 收到了广播也会被系统拦)。

界面会把状态直接打出来: `电池白名单: 已加入 ✓` / `未加入 ✕`。

验证方式:

```
adb shell dumpsys deviceidle whitelist | grep blekey     # 有记录 = 已加入白名单
adb shell dumpsys jobscheduler | grep -A6 KeepAliveJob   # PERIODIC interval=+15m + PERSISTED
adb shell dumpsys alarm | grep KEEPALIVE                 # flags=0x8 = ALLOW_WHILE_IDLE
```

## 靠近自动开锁(距离阈值)

**判断距离这件事由车机做, App 只负责下发阈值。**

车机通过 `cmd=7 key=32` 回报舒适进入参数, BleKey 连上后会自动读一次, 显示在车辆的
「靠近自动开锁 / 落锁·开锁距离」两行里:

```
靠近自动开锁      已开启
落锁 / 开锁距离   -80 / -70 dBm
```

payload 布局(`SystemCFGResp`): `[0]=是否开启`, `[1..2]=落锁距离 u16LE`,
`[3..4]=开锁距离 u16LE`, `[5..8]=错误码 u32LE`。距离是 RSSI 的**绝对值**, 70 表示 -70dBm;
开锁要求信号更强(数值更小)才触发, 70 与 80 之间是回差区间, 避免在边界反复开关。

车机还会每 2 秒主动推一次 `cmd=4 key=107`(RSSI 绝对值, `0x24` = 36 → -36dBm),
BleKey 用这条推送刷新状态行的信号强度, 有推送时就不再自己 `readRemoteRssi`。

### 改阈值: 高级设置 → 落锁与开锁阈值

写入用 `cmd=7 key=0`, payload `[0]开关 + [1..2]落锁 u16LE + [3..4]开锁 u16LE`, 共 5 字节。
车盒对这条**不回执**(原包也不等), 所以写完 700ms 重发一次 `7/32` 用真实值校准 ——
低电量时车盒会自己把舒适进入关掉, 只有重读才能发现。

界面提供三段式调节: 总开关 + 两个滑块(-45 ~ -95 dBm, 步进 5) + 恢复默认。

**「恢复默认」写回的是基线, 不是硬编码值。** 基线 = 第一次从车机读到的实测标定
(这台车是 落锁 -80 / 开锁 -70), 只建立一次。不用原包那套 `75/65`, 那是它打开总开关时的
初值, 每台车盒标定不同; 也不用"当前值", 因为参数被改坏之后再点重置, 当前值已经是坏值了。

校验规则: 开锁必须比落锁更强(数值更小), 否则会出现"走远了也不落锁", 车停着不锁。
两档相差超过 25dBm 会提示可能走到车边不开锁。

> App 不自己判距离。车机已经在做这件事, 客户端再判一次就会各开一遍。

## 开锁 / 落锁的车机约定

这两条规则**不是 App 定义的, 是车机里保存的配置**。原 App 的配置页只是把服务器下发的
十六进制配置串写进车机(`cmd=7 key=4` 开锁配置 / `key=1` 关锁配置), 规则本身存在车里。
所以换了客户端, 规则照样生效, 客户端必须按同样的节奏发指令。

| 动作 | 车机配置 | BleKey 的实现 |
|---|---|---|
| 开锁 | 按 2 次, 间隔 1 秒 | 点一次「解锁」连发 2 帧 `cmd=4 key=100`, 间隔 1000ms(`Prefs.UNLOCK_GAP_MS`) |
| 落锁 | 关锁后及时断电 | 单发 1 帧 `cmd=4 key=101`; 之后 15 秒内不主动重连(`LOCK_QUIET_MS`), 给车机断电留时间 |

### 为什么不"直接读原 App 的配置"

查过原始实现, 这条路走不通, 但也不需要:

1. **车机没有"读锁配置"的指令**。`FtkSend` 里 `carLockConfig(7/1)`、`carUnLockConfig(7/4)`、
   `carRemoteStartUpConfig(7/3)` 全是 setter; 唯一能读回的是舒适进入参数 `7/32`。锁配置只能写, 读不回来。
2. **原 App 本地也不存内容**。`CftConfig.content`(十六进制串)来自服务器 `queryCftConfigs`,
   本地只缓存选中的 `id`。而且它在原 App 的 `/data/data/<package>/` 私有目录, 无 root 读不到。
3. **规则本来就跑在车机里**, 换客户端照样生效, 客户端只要按同样节奏发帧。

所以 BleKey 不去读配置, 直接固定「开锁 2 帧 / 间隔 1 秒」。如果哪天在原 App 里把配置改成
「按 1 次」, 后果只是多发一帧解锁指令(不会误锁), 需要时改 `Prefs.unlockTwice()` 返回 false 重新出包。

> BleKey **不会**去改车机的开锁/落锁配置, 只按上面的节奏发指令。

## 电量显示

电量不是单独的命令, **它就是「系统信息同步」那条回复**(`cmd=2 key=0`)里的一个 TLV 字段。

流程(与原 App 完全一致):

```
鉴权通过 → 手机发 cmd=2 key=0 (TLV: 时间戳/时区/语言, 顺带同步车机时钟)
        → 车机回 cmd=2 key=0, payload 一串 TLV, 其中 tag=23 就是电量百分比
        → BleKey 解析后存起来, 界面卡片和通知栏显示
```

payload 实测(Redmi + 车盒固件 1.2.2):

```
17 01 64                         tag=23 len=1  电量 100%
18 02 01 00                      tag=24 版本主 1
19 02 02 00  1a 02 02 00          tag=25/26 版本 2.2
1b 04 02 00 00 00                tag=27 设备类型 2 = 车盒
1c 04 02 00 00 00                tag=28 平台 2 = NORDIC
1d 04 xx xx xx xx                tag=29 配对号（示例值已脱敏）
1e 01 01                         tag=30 绑定状态 1 = 已绑定
20 02 3b 0f                      tag=32 电压 0x0F3B = 3899 mV
21 01 00                         tag=33 充电状态
22 01 00                         tag=34 车盒电源状态
23 04 xx xx xx xx                tag=35 车型（示例值已脱敏）
1f 08 xx xx xx xx xx xx xx xx    tag=31 CPU ID（示例值已脱敏）
```

要点:

- 电量是**单字节**百分比(0x64 = 100), 与原 App `resp.setPower(content[0])` 一致
- 电压是 **2 字节小端**, 单位 mV; 车盒是 3.9V 锂电池, 稳定在 3896~3903mV
- 有的固件会先回显手机发去的 tag(1/2/3/4/19)再回自己的 tag, 所以按 tag 取值, 不靠顺序
- 车机偶尔会**连回两条一模一样的帧**(实测间隔 120ms), 后到覆盖前到即可
- 原 App 的取值时机: 鉴权通过后(`authOk` → `setSystemInfo`)以及**设备页下拉刷新**时;
  没有定时轮询。BleKey 沿用这个策略, 另外在界面 onResume 且数据超过 60 秒时补一次

界面上显示为一张卡片: 左侧环形(百分比在圆心) + 右侧电压与更新时间, ≤20% 变红提示(与原 App 的低电量弹窗阈值一致)。
通知栏追加 `· 电量 100% · 3.90V`。断开后保留最后一次读到的值并标注"当前未连接"。

> tag=33(充电状态)与 tag=34(车盒电源状态)在实测里会**各自独立跳变**, 语义未确认,
> 因此只记录进日志、不在界面上断言"充电中", 避免给出错误信息。

## 协议参考

帧头 16 字节, 小端:

```
[0..1]   55 AA (上行) / AA 55 (下行)
[2]      version
[3]      type | channel<<4
[4..5]   sequenceId
[6..7]   cmd
[8..9]   key
[10..11] payload 长度
[12..13] payload 字节求和
[14..15] 头部 [0..13] 字节求和(含上一条)
+ payload
```

> 校验是**逐字节求和**, 不是 CRC(原 App 里函数名叫 `crc8WithData`, 实现是 `sum += b[i] & 0xFF`)。

TLV: `tag(1B) + len(1B) + value`; int 固定 4B LE, short 2B LE, byte 1B。

密钥派生(与原 App 完全一致):

```
deviceKey = AES-ECB-NoPadding( pad(password, 16), pad(车机序列号Hex大写, 16) )
keyPass   = hex(deviceKey)          // 32 字符, 存本地
校验时:   AES-ECB-NoPadding( keyPass, 车机下发的 random(16B) )
password  = 6 位数字, 由手机端生成(不依赖服务器)
```

常用指令:

| 功能 | cmd | key | payload |
|---|---|---|---|
| 请求鉴权 | 6 | 0 | — |
| 下发设备密钥 | 6 | 1 | deviceKey(16B) |
| 校验设备密钥 | 6 | 2 | AES(keyPass, random) |
| 解绑 | 6 | 3 | — |
| 请求车机手动确认 | 6 | 4 | — |
| 快速解锁 | 4 | 100 | — |
| 快速落锁 | 4 | 101 | — |
| 快速开后备箱 | 4 | 115 | — |
| 远程启动 | 4 | 106 | — |
| 降窗 | 4 | 114 | — |
| 读 RSSI | 4 | 107 | — |
| 舒适进入配置(写) | 7 | 0 | 1B 开关 + 2B 落锁距离 + 2B 开锁距离 |
| 舒适进入参数(读) | 7 | 32 | 响应: 1B 开关 + 2B 落锁距离 + 2B 开锁距离 + 4B 错误码 |
| 系统信息同步 | 2 | 0 | TLV(时间/时区/语言); **响应里含电量** |

`cmd=2` 响应 TLV(tag 与原 App `TlvTag` 一致):

| tag | 含义 | 长度 | 说明 |
|---|---|---|---|
| 23 | 电量 | 1B | 百分比 0~100 |
| 24/25/26 | 版本 主/次/修订 | 2B | 1.2.2 |
| 27 | 设备类型 | 4B | 1 车钥匙 / 2 车盒 |
| 28 | 平台 | 4B | 1 ATK / 2 NORDIC / 3 REALTEK / 4 ONMICRO / 5 REALTEK8773 |
| 29 | 配对号 | 4B | |
| 30 | 绑定状态 | 1B | 0 未绑定 / 1 已绑定 |
| 31 | CPU ID | nB | |
| 32 | 电池电压 | 2B | mV, 小端 |
| 33 | 充电状态 | 1B | 语义未确认, 仅记录 |
| 34 | 车盒电源状态 | 1B | 语义未确认, 仅记录 |
| 35 | 车型 | 4B | |

GATT:
- 服务 `8849a9d0-d75f-0c8c-2348-de2d580f2f24`
- 收发特征 `8849a9d1-d75f-0c8c-2348-de2d580f2f24`(写 + notify, 同一特征)
- 日志特征 `8849a9d2-d75f-0c8c-2348-de2d580f2f24`
- MTU 247, 写类型 `WRITE_TYPE_NO_RESPONSE`
- 广播厂商 ID `0xF715 (63253)`, 厂商数据前 6 字节 = 车机序列号

## 已知限制

1. **必须先在原 App 里解绑旧设备**, 否则配对会被拒(会提示)
2. 连接是独占的, 和原 App 不能同时用 —— 用「让给原 App(10 分钟)」切换
3. 首次配对需要车机在附近; 之后 autoConnect 白名单会一直记着这台车
4. Android 12+ 需要给通知权限, 否则前台服务不显示(连接仍继续)
5. 部分 ROM(含 HyperOS)会主动清理后台, 记得加电池白名单和自启动
6. 车机锁配置无法读回(见上文), 开锁节奏写死在代码里
